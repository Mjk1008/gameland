# ۳۷ — بازطراحیِ صفحه‌ی «امروز»: استوری + چیدمانِ ساده‌شده

**Stage:** Plan (اجرا نشده) · **Status:** 📝 نوشته‌شده، بعد از بنچ‌مارکِ Opus روی کدِ واقعی تصحیح شده، بعد با یه گفتگوی طراحی چیدمانِ کلِ صفحه هم بهش اضافه شده
**پیش‌نیاز:** [`docs/35-live-day-hub-plan.md`](35-live-day-hub-plan.md)، [`docs/36-live-day-hub-design-brief.md`](36-live-day-hub-design-brief.md) — این سند رو `/today` (که آماده‌ست) می‌سازه.

> بخش‌های ۰ تا ۸ (استوری) یه درفتِ اول بود که با یه سشنِ Opus روی کدِ واقعیِ ریپو بنچ‌مارک و تصحیح شد. بخشِ ۹ به بعد اضافه شد چون معلوم شد چیدمانِ فعلیِ `/today` (کارتِ چک‌این + فیدِ ترکیبی) هم باید عوض بشه — نه صرفاً «یه نوارِ استوری بذار بالاش».

---

## ۰. شکلِ محصول

**یه کانالِ واحدِ ادمین‌ساخته، نه استوریِ پرکاربر.** ادمین عکس/ویدیو آپلود می‌کنه، همه می‌بینن. حلقه‌های رنگی بالای `/today` (بالای HeroCard)، تپ → ویوئرِ تمام‌صفحه با اتوپلی، پراگرس‌بارِ بخش‌بندی‌شده، تپ برای جلو/عقب، نگه‌داشتن برای پاز، سواپِ رو به پایین برای بستن، ✕ صریح. بعد از ۲۴ ساعت خودکار حذف می‌شه؛ ادمین هم می‌تونه زودتر پاکش کنه.

**تصمیمِ اصلیِ این سند نسبت به چیزی که اول درخواست شده بود: نسخهٔ اول فقط عکسه، ویدیو نه.** دلیلش بخشِ ۱ رو بخون — این تصمیمِ معماریه، نه سلیقه.

---

## ۱. چرا ویدیو نه — نسخهٔ اول فقط عکس

این اپ `scale: 1` هست و هر بلاب (عکسِ پروفایل، فیش، کاورِ خبر) از قبل base64 توی یه ستونِ TEXT پستگرس ذخیره می‌شه و **کامل** به RAM خونده می‌شه موقعِ سرو (`app/api/avatar/[id]/route.ts` — همون پترنِ دقیقی که این استوری هم قراره ازش کپی کنه). این برای یه عکسِ ۲۰۰KB بی‌خطره.

برای ویدیو نیست:
- یه کلیپِ ۸MB می‌شه ~۱۱MB متنِ base64 تو دیتابیس، که هر بار سرو می‌شه کامل از پستگرس بیرون کشیده می‌شه و تو همون پروسه‌ای که کل استیت زنده‌ی اپ (کاربرا، براکت‌ها، مسابقات) روشه بافر می‌شه. ۲۰ نفر هم‌زمان رو یه روزِ مسابقه یعنی صدها مگابایت تخصیصِ موقت رو یه پروسه‌ی تک‌نسخه‌ای — اگه کرش کنه، ثبت‌نام و براکت هم باهاش می‌ره.
- پخشِ ویدیو (خصوصاً iOS Safari) بدونِ پشتیبانیِ **HTTP Range/206** اصلاً درست کار نمی‌کنه؛ پیاده‌سازیِ درستِ Range رو یه ستونِ TEXT-base64 (نه فایل) نیازمندِ محاسبهٔ align رو مرزِ ۴-کاراکتریِ base64 است — پیچیدگیِ واقعی، نه یه هدرِ ساده.
- هیچ مسیرِ ویدیوی دیگه‌ای تو این کدبیس وجود نداره که ازش الگو بگیریم — همه‌چیز از صفره.
- سایزِ بدنه‌ی درخواست (base64 ۸MB ~۱۱MB JSON) هیچ‌وقت رو این استک/پراکسیِ لیارا تست نشده — بزرگ‌ترین آپلودِ فعلیِ اپ فیشه، حدودِ ۲.۲MB دیکد شده.

**پیشنهاد:** نسخهٔ اول فقط عکس. اگه بعداً ویدیو لازم شد، دو راهِ صادقانه هست: (الف) استوریج آبجکتِ لیارا با URL مستقیم — یه وابستگیِ جدید که باید صریح تاییدش کنی، یا (ب) کلیپِ خیلی کوتاه/سبک (≤۶ ثانیه، ≤۲MB، بی‌صدا) که عملاً یه گیفِ گرون‌تره. اینو به‌عنوانِ «کارِ بعدی» جدا نگه می‌داریم، تو اسکوپِ این پلن نیست.

## ۲. مدلِ داده

```ts
// lib/store.ts
interface Story {
  id: string
  createdAt: number          // epoch ms
  expiresAt: number          // epoch ms — createdAt + STORY_WINDOW_MS، ذخیره می‌شه نه مشتق،
                              // که تغییرِ بعدیِ عددِ ۲۴ساعته چیزای قدیمی رو زنده نکنه
  createdBy: string          // ادمینی که آپلود کرده
  removedAt?: number         // حذفِ زودهنگامِ ادمین (فقط متادیتا نگه داشته می‌شه، بایت‌ها فوراً پاک می‌شن — بخشِ ۵)
}
export const STORY_WINDOW_MS = 24 * 3600_000   // یه ثابتِ export‌شده، تا تستِ expiry بدونِ صبرِ واقعیِ ۲۴ساعت ممکن باشه
```

- **`stories: Map<string, Story>`** — کوچیک، بدونِ بایت، تو RAM.
- **`storyViews: Map<string, Set<string>>`** (`storyId → Set<userId>`) — کی دیده.
- بایت‌ها تو ۲ جدولِ جدا (عکسِ اصلی + تامبنیلِ کوچیک؛ بخشِ ۵ توضیح می‌ده چرا جدا):

هر جدول/فیلدِ جدید طبقِ قاعده‌ی این ریپو باید **همزمان** این ۵ تیکه رو داشته باشه (نه فقط DDL — این دقیقاً همون چیزیه که یه بار `MatchDesk` رو شکست، docs/35 §3):
1. تایپِ `pgTable` تو `lib/db/schema.ts`
2. DDLِ خودترمیم‌شونده (`CREATE TABLE IF NOT EXISTS`) تو `lib/db/persistence.ts`
3. هلپرهای Drizzle (`persist.story.*`, `persist.storyMedia.*`, `persist.storyView.*`) — این اپ از SQL خام برای persist استفاده نمی‌کنه، از آبجکت‌های Drizzle (مثلِ `persist.avatar`)
4. لودرِ hydration تو `startHydration()`
5. صدا زدنِ اون لودر تو `ensureHydrated()` (`lib/store.ts`)

```sql
CREATE TABLE IF NOT EXISTS app_stories (
  id TEXT PRIMARY KEY, created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  expires_at TIMESTAMPTZ NOT NULL, created_by TEXT NOT NULL, removed_at TIMESTAMPTZ
);
CREATE TABLE IF NOT EXISTS app_story_media (id TEXT PRIMARY KEY, data_url TEXT NOT NULL, thumb_data_url TEXT NOT NULL);
CREATE TABLE IF NOT EXISTS app_story_views (story_id TEXT NOT NULL, user_id TEXT NOT NULL, viewed_at TIMESTAMPTZ NOT NULL DEFAULT now(), PRIMARY KEY (story_id, user_id));
```

نکته‌های ریز ولی مهم که تو درفتِ اول نبودن:
- **تبدیلِ `TIMESTAMPTZ` ↔ epoch باید صریح باشه.** اگه هیدریشن این تبدیل رو جا بندازه، `expiresAt` می‌شه `NaN`، همه‌چی «منقضی» به نظر می‌رسه، و کل بار خالیه بدونِ هیچ خطایی — دقیقاً همون کلاس باگی که این پروژه داره ازش فرار می‌کنه.
- **`app_story_media` تامبنیلِ ۱۲۰پیکسلیِ خودشو جدا نگه می‌داره** (`thumb_data_url`، چند KB) — چون رندرِ حلقه‌های ۵۶پیکسلی از عکسِ اصلیِ ۱۴۰۰پیکسلی همون اشتباهِ «هوم‌پیجِ ۷.۴مگابایتی»یِ CLAUDE.md به‌صورتِ مینیاتوره.
- **`kind` حذف شد** — نسخهٔ اول همه عکسه، نیازی به این فیلد نیست (اگه ویدیو بعداً اضافه شد، همون‌جا برمی‌گرده).
- **حذفِ ادمین = soft-delete رو `app_stories` (برای audit/شمارشِ ویو)، ولی hard-delete فوریِ ردیفِ `app_story_media`.** یه استوریِ اشتباه که ادمین پاکش کرده معمولاً یعنی محتواش غلطه — نباید بایتش هنوز از مسیرِ مستقیم قابلِ‌فچ بمونه.
- **پرونینگِ `app_story_views` اختیاری نیست:** رو هیدریشن، ویوهای مربوط به استوری‌های بیش از ۷ روز منقضی‌شده حذف بشن — وگرنه این جدول بی‌نهایت رشد می‌کنه و کاملش هر بار میاد تو RAM.

## ۳. مسیرهای API

همه از `withTodayUser` (`lib/today-hub-http.ts`) رد بشن — یعنی اگه `TODAY_HUB_ENABLED` خاموش باشه، این مسیرها هم مثلِ بقیه‌ی `/today` چهارصدوچهار می‌دن، نه اینکه جدا از گیت اصلی کار کنن.

| Route | کار |
|---|---|
| — (داخلِ `buildTodaySnapshot(uid)`) | لیستِ استوریِ فعال + `seen` برای هر آیتم، **همون snapshot موجودی که هر ۸ثانیه پول می‌شه** — نه یه پولِ جدا. (بخشِ ۴ می‌گه چرا این تصمیمِ اجباریه، نه انتخابی.) |
| `POST /api/today/stories/view` | بدنه: `{ ids: string[] }` — batch، نه یکی‌یکی (بخشِ ۴). Idempotent (`ON CONFLICT DO NOTHING`). |
| `GET /api/story-media/[id]` | سرو کردنِ عکسِ اصلی. **قبل از خوندنِ دیتابیس، از رویِ Mapِ RAM چک کنه `expiresAt > now && !removedAt`** — وگرنه یه لینکِ مستقیم، استوریِ منقضی/حذف‌شده رو تا ابد قابلِ‌دیدن نگه می‌داره. `Cache-Control: public, max-age=31536000, immutable` (بایتِ هر id تغییر نمی‌کنه) — با این‌که یعنی حذفِ زودهنگام نمی‌تونه نسخه‌ی از‌قبل‌کش‌شده رو پس بگیره؛ اگه این مهمه، `no-store` بذار و هزینه‌ی دانلودِ دوباره رو بپذیر (تصمیمِ محصولیه، نه کد). `dynamic = 'force-dynamic'`. |
| `GET /api/story-media/[id]/thumb` | همون، برای `thumb_data_url`. |
| `POST /api/admin/stories` | آپلودِ ادمین: `{ imageData }` (data URL). چکِ نقش: **فقط `role === 'admin'`** (نه organizer — تصمیمِ صریحِ کاربر، بخشِ ۱۰.۵؛ برخلافِ پترنِ `admin \|\| organizer`ی که `app/api/admin/news/route.ts` داره). ردیفِ Story + بایتِ اصلی + تامبنیل تو **یه** فراخوانی ساخته می‌شن (نه دو مرحله — همون اصلی که تو فیکسِ فیش/ثبت‌نامِ همین سشن اعمال شد: هیچ‌وقت یه چیزِ نصفه‌ساخته نمونه). |
| `POST /api/admin/today-announcements` | نوشتنِ اعلان: `{ text }`. همون چکِ نقش (`role === 'admin'`). |
| `DELETE /api/admin/today-announcements/[id]` | حذفِ یه اعلان (soft، `removedAt`). |
| `DELETE /api/admin/stories/[id]` | `removedAt` رو ست می‌کنه، ردیفِ `app_story_media` رو فوری پاک می‌کنه. |
| `GET /api/admin/stories` | لیستِ ادمین: تامبنیل، زمانِ ساخت، شمارشِ ویو، دکمه‌ی حذف. جدیدترین اول. |

## ۴. ویوئرِ تمام‌صفحه — پرریسک‌ترین بخش (دقیقاً همونی که نگرانشی)

### ۴.۱ تصمیمِ اجباری: لیست از کجا میاد
News رو `/today` سمتِ سرور رندر می‌شه (props)، فقط خودِ اسنپ‌شات پول می‌شه (`use-polling.tsx`، ۸ثانیه، بک‌آفِ تبِ مخفی). پس استوری هم باید **داخلِ همون `TodaySnapshot`** باشه، نه یه پولِ جداگونه — این تضمین می‌کنه `seen` per-uid همیشه با بقیه‌ی صفحه هم‌زمانه.

**نکته‌ی حیاتی که تو درفتِ اول نبود:** چون لیست هر ۸ ثانیه پول می‌شه، اگه ویوئرِ بازه و یه استوری وسطِ دیدن منقضی/حذف بشه یا یکی جدید بیاد، ایندکسِ زیرِ پای کاربر جابه‌جا می‌شه (فریمِ خالی یا پرش به استوریِ غلط). **راه‌حل: ویوئر لحظه‌ی باز شدن یه snapshot از لیست می‌گیره و تا بسته شدن دیگه از پول تازه نمی‌خونه.**

### ۴.۲ ترتیب: جدیدترین‌اول، نه ندیده‌اول
درفتِ اول «ندیده‌ها اول» پیشنهاد داده بود. **برگردوندمش به جدیدترین-اول همیشه** (رنگِ حلقه دیده/ندیده رو نشون می‌ده، نه جای آیتم) — چون:
- این دقیقاً همون قاعده‌ی خودِ CLAUDE.md‌ه («لیست‌ها همه‌جا جدیدترین-اول»)،
- جلوی این باگ رو می‌گیره: با ندیده‌اول، دیدنِ یه استوری باعثِ جابه‌جاییِ خودِ نوار زیرِ انگشتِ کاربر می‌شه،
- کل پیچیدگیِ «رو تیکِ پول دوباره سورت نکن مگه چیزی عوض شده» رو حذف می‌کنه.

### ۴.۳ یه state machine، نه سه تشخیص‌دهنده‌ی رقیب
درفتِ اول تپ/نگه‌داشتن/سواپ رو سه بولتِ جدا نوشته بود بدونِ اینکه بگه کدوم رو کدوم غالبه — دقیقاً جایی که «تپ‌ها بد اتفاق می‌افته» از اینجا میاد. یه مدلِ واحد:

state: `{ index, phase: 'loading'|'playing'|'paused'|'errored', elapsedMs, gen }` + اسکرچِ پوینتر `{ x0, y0, t0, dragging }`

- **`pointerdown`** → فوراً پاز کن (نه بعد از تاخیر)، `x0,y0,t0` رو ذخیره کن.
- **`pointermove`** → اگه `|dy| > 10px` بشه `dragging=true`، شیت رو ترنسلیت کن، تپ/هولد لغو بشه.
- **`pointerup`** → اگه `dragging && dy > 80` ببند؛ اگه `dragging` بدونِ عبور از آستانه برگردون سرِ جاش و ادامه بده؛ اگه `t − t0 < 250ms` یعنی تپ بود (زون از رویِ `getBoundingClientRect()` **همون لحظه**، نه سایزِ mount)؛ وگرنه هولد بود → ادامه بده.

این یه مدل جوابِ همه‌ی این‌ها رو می‌ده بدونِ قانونِ جدا برای هرکدوم:
- **تپِ سریع اشتباهی هولد تشخیص داده نشه** (آستانه‌ی «هولد بعدِ ۱۵۰ms» یه dead-zone داره: یه تپِ ۱۶۰ms هیچ اتفاقی نمی‌افته — پاز-رو-pointerdown این مشکل رو کلاً حذف می‌کنه).
- **دبل‌تپِ سریع/اسپم‌کردنِ next** — تغییرِ index باید synchronous و با `setState` تابعی باشه (نه منتظرِ لودِ مدیا)، تا دو تپ تو یه فریم رو ایندکسِ باسیات نخونن؛ رویِ آخرین آیتم clamp بشه نه رد بشه.
- **تپ درست وسطِ لودِ استوریِ بعدی** — یه شماره‌ی نسل (`gen`) موقعِ شروعِ لود بگیر و تو کال‌بکِ لود چک کن؛ وگرنه تایمرِ استوریِ اشتباه استارت می‌خوره.
- **پس‌زمینه رفتنِ تب/قفل‌شدنِ گوشی** — `visibilitychange` (دقیقاً همون الگویی که `use-polling.tsx` از قبل داره): موقعِ hidden پاز کن و elapsed رو نگه‌دار؛ موقعِ visible از همون elapsed ادامه بده (نه از صفر، نه skip).
- **چرخشِ صفحه/تغییرِ سایز** — زون‌های تپ همیشه از `getBoundingClientRect()` تازه محاسبه بشن. اورلی رو `position: fixed; inset: 0` بذار، نه `height: 100vh` — هم مشکلِ vh/dvh حل می‌شه، هم تغییرِ سایزِ نوارِ آدرسِ سافاری وسطِ استوری.
- **فقط یه استوری تو کل لیست** — یه سگمنتِ تمام‌عرض؛ «قبلی» ریستارتش می‌کنه؛ آخرش می‌بنده.
- **همون یکی هم لود نشد (خطای شبکه)** — با N=1، «برو بعدی» یعنی ویوئر باز می‌شه و فوراً خودش می‌بنده — این باید یه حالتِ جدا باشه («همه ناموفق بودن»: یا با دکمه‌ی تلاشِ‌دوباره باز بمونه، یا با توستِ خطای موجودِ اپ ببنده). متنِ دقیقش رو خودت بگو (قاعده‌ی بدونِ‌متنِ‌جدید).
- **✕ همیشه کار کنه** — این باید رو لایه‌ای بالاترِ زونِ تپ باشه که رو `pointerdown` (نه `onClick`) با `stopPropagation` جلوی رسیدنِ تپ به زیرش رو بگیره؛ حداقل ۴۴px هدفِ لمسی.
- **سواپِ رو به پایین با اسکرولِ خودِ صفحه قاطی نشه** — رویِ سطحِ ژست `touch-action: none` بذار (وگرنه مرورگر قبل از هندلرِ خودت درگ رو قاپ می‌زنه)، و `body { overflow: hidden }` تا ویوئر بازه (وگرنه سافاری پشتِ اورلی رابر-بند می‌کنه و با سواپت می‌جنگه).
- **دکمه‌ی بک (سخت‌افزاری/PWA)** — موقعِ باز شدن یه history entry پوش کن، موقعِ بستن پاپش کن؛ وگرنه بک از کلِ `/today` بیرون می‌ندازه کاربر رو، نه فقط ویوئر رو.

### ۴.۴ چیزهای دیگه‌ی این بخش
- پراگرس‌بار: **جهتِ پر شدن همیشه چپ‌به‌راست باشه** (کانتینر `direction:'ltr'`، دقیقاً همون پترنی که `today-news-rail.tsx` از قبل برای نوارِ افقی استفاده می‌کنه) — نه چیزِ جدید، فقط تکرارِ همون قاعده.
- تایمر تا وقتی مدیا واقعاً لود نشده (`onLoad`) شروع نشه — این مهم‌ترین قانون در برابرِ «تایمِ اتوپلی بد» و تو درفتِ اول هم درست بود، دست‌نخورده موند.
- پیش‌بارگذاری فقط N و N+1 (نه همه‌ی لیست همزمان — وگرنه دوباره میفتیم تو مشکلِ دانلودِ زیاد).
- «دیده‌شدن» batch می‌شه: idهای دیده‌شده سمتِ کلاینت جمع می‌شن، یه POST موقعِ بستنِ ویوئر + یه POST رو `visibilitychange→hidden` (که یه بستنِ ناگهانیِ اپ گمشون نکنه) — نه یه POST به‌ازای هر استوری، رو نتِ ایرانی.
- z-index باید بالاتر از `NavProgress` (۱۰۰، بالاترین موجود) باشه — پیشنهاد ۱۱۰+.
- ✕ رو دقیقاً از رویِ `app/news-story-modal.tsx` کپی کن (سایز، رنگ، بلور، انیمیشنِ خروج) — همون کامپوننتی که همین الان تو `/today` این کارو می‌کنه، پس هم ظاهرش با بقیه‌ی اپ یکیه، هم چیزی اختراع نشده.

## ۹. چیدمانِ جدیدِ `/today` (بالا به پایین)

```
۱. نوارِ استوری                         (بخشِ ۰-۸ همین سند)
۲. کارتِ «مسابقه‌ی بعدیم» — فقط‌نمایشی، بدونِ دکمه‌ی چک‌این
۳. دکمه‌ی «مسیرِ من»                     (لینک به /competitions/[id]/me — از قبل ساخته شده)
۴. تابلوِ اعلان — تاریخچه‌ای، فقط‌متنی
۵. بخشِ زنده — رویداد → استان → فیدِ زنده (درختِ تعاملی، نه سه ویجتِ جدا)
```

### ۹.۱ کارتِ «مسابقه‌ی بعدیم» — حذفِ چک‌این
تصمیم: **دکمه‌های «حاضرم»/«آماده‌ام»/«درخواستِ داور» از `HeroCard` حذف می‌شن.** کارت فقط اطلاعات نشون می‌ده — حریف، دور، امتیاز اگه بازی درحالِ انجامه — بدونِ هیچ اکشنی. state‌های `none`/`waiting`/`playing`/`advanced`/`eliminated` (از `lib/today-snapshot.ts`) همون‌ها می‌مونن، فقط CTAهای تعاملی‌شون حذف می‌شن؛ خودِ کارت دیگه tap-to-open-sheet هم لازم نداره چون چیزی برای انجام‌دادن توش نیست.

**یه پیامد که باید بدونی، نه چیزی که خودم بی‌سروصدا حذف کنم:** الان تختهٔ ادمینِ `/admin/today` (station-grid، دکمه‌ی «صدا کن») رو سیگنالِ «کاربر خودش زد حاضرم/آماده‌ام» حساب باز کرده بود (`MatchDesk.p1Here/p1Ready`). اگه این دکمه‌ها از سمتِ بازیکن حذف بشن، اون سیگنال دیگه هیچ‌وقت از سمتِ بازیکن ست نمی‌شه — تختهٔ ادمین یا باید فقط رو دیتای موجود (اسم/حریف/دور) کار کنه بدونِ ستونِ «حاضر/آماده»، یا ادمین خودش دستی این وضعیت رو تیک بزنه. **این یه تصمیمِ جداست که باید بگی**: تختهٔ ادمین رو هم ساده کنیم (فقط دیدنِ کیو صدا کنه، بدونِ چک‌باکسِ حاضر/آماده)، یا اصلاً نسازیمش تو این فاز و بذاریم برایِ بعد؟

`HeroState.waiting` الان `compId` نداره تو تایپش (`{ kind:'waiting'; roundLabel:string }`) — برایِ اینکه دکمه‌ی «مسیرِ من» زیرِ این حالت هم کار کنه، باید `compId` بهش اضافه بشه تو `deriveHeroState()`.

**قانونِ نمایش (جوابِ صریح به «کسایی که تو مسابقه نیستن یا بازیشون تموم شده نبینن»):**

| حالتِ `hero.kind` | کارتِ «مسابقه‌ی بعدیم» | دکمه‌ی «مسیرِ من» |
|---|---|---|
| `none` (اصلاً تو هیچ رویدادِ liveـی ثبت‌نامِ فعال نداره) | ❌ نه | ❌ نه (چیزی برایِ لینک‌شدن نیست) |
| `eliminated` (بازیش تموم شده، حذف شده) | ❌ نه — دیگه «بازیِ بعدی» نداره که نشون بده | ✅ آره — مسیرِ نهایی/جایگاهش تو براکت هنوز دیدنیه |
| `waiting` / `ready` / `playing` / `advanced` (هنوز تو رویداده) | ✅ آره (ساده‌شده، بدونِ CTA) | ✅ آره |

یعنی برایِ دو گروهِ اول، صفحه مستقیم از استوری می‌ره سراغِ تابلوِ اعلان + بخشِ زنده (§۹.۳, §۹.۴) — هیچ جای خالی/پیامِ جایگزین («بازیِ فعالی نداری») نمی‌ذاریم، دقیقاً چون اون کاربر همون چیزایی که «می‌مونه» (فید، استوری، اعلان) رو می‌بینه و کارتِ اختصاصی براش بی‌معنیه.

### ۹.۲ دکمه‌ی «مسیرِ من»
هیچ صفحه‌ی جدیدی لازم نیست — `/competitions/[id]/me` از قبل دقیقاً همین کارو می‌کنه (روندِ راند‌به‌راند، وضعیتِ سهم‌ها، لینکِ براکتِ کامل). جدولِ بالا می‌گه دقیقاً کِی نشون داده بشه.

### ۹.۳ تابلوِ اعلان — تاریخچه‌ای
مکانیزمِ فعلی (`AdminAnnouncementBanner`) فقط آخرین اعلان رو تا ۳ ساعت نشون می‌ده، از رویِ صفِ نوتیفِ شخصیِ خودِ کاربر (`notifsForUser`). این برایِ یه **تابلویِ مشترکِ تاریخچه‌ای** مدلِ درستی نیست — چون یعنی هزار کاربر هزار کپیِ جداگونه از یه متنِ ثابت تو RAM دارن، و ادمین نمی‌تونه یه اعلانِ مشخص رو ویرایش/حذف کنه چون هیچ id مشترکی نداره.

**مدلِ جدیدِ پیشنهادی** (سبک، چون فقط متنه — نیازی به جدولِ بلاب نداره):
```ts
interface TodayAnnouncement { id: string; text: string; createdAt: number; createdBy: string; removedAt?: number }
```
یه جدولِ خودترمیم‌شونده‌ی معمولی (نه بلاب)، هیدریت می‌شه کامل تو RAM (متن کوچیکه). تابلو = لیستِ این‌ها، جدیدترین اول، فیلترِ `!removedAt`. اعلانِ ادمین همچنان می‌تونه (اختیاری) یه `pushNotif` هم بفرسته برایِ پوش/زنگ، ولی خودِ تابلو مستقیم از این جدولِ مشترک می‌خونه، نه از صفِ نوتیفِ هرکسی.

ادمین از همون بخشِ آپلودِ استوری (یا کنارش، تو `/admin/today`) متن می‌نویسه و می‌فرسته — یه فرمِ ساده‌ی تک‌خطی، نه چیزِ جدیدی.

### ۹.۴ بخشِ زنده — درختِ تعاملیِ رویداد ← استان ← فید
الان سه ویجتِ جدا داریم که هیچ‌کدوم بهم لینک نیستن: `LiveFeed` (فیدِ کلِ رویدادهایِ live قاطی‌شده)، `ProvincePulseStrip` (نوارِ پیشرفتِ استان‌ها، **بدونِ هیچ onClick — چک کردم، تو کدِ فعلی صرفاً نمایشیه**، برخلافِ چیزی که docs/35 آرزو کرده بود).

تصمیم: این سه‌تا با هم ادغام می‌شن به یه drill-down:
1. اگه بیش از یه رویدادِ live هم‌زمان باشه → یه ردیفِ چیپ برایِ انتخابِ رویداد (اگه فقط یکی باشه، این مرحله رد می‌شه).
2. زیرش، نوارِ استان‌هایِ همون رویداد (کارت‌های فعلیِ `ProvincePulseStrip`، حالا **تپ‌شونی**).
3. تپ رو یه استان → همون‌جا (نه ناوبریِ صفحه‌ی جدا) `LiveFeed` فقط نتایجِ همون رویداد+استان رو نشون می‌ده.

برایِ این، `ProvincePulse` و `FeedItem` (تو `lib/today-snapshot.ts`) باید `compId` رو هم حمل کنن (الان `FeedItem` فقط `matchId/winnerName/loserName/score/completedAt` داره، `compId` نداره) تا فیلترِ سمتِ کلاینت بدونِ درخواستِ اضافه ممکن باشه — کل دیتا از همون `TodaySnapshot`یِ موجود میاد، فقط دو فیلد بهش اضافه می‌شه.

### ۹.۵ باگِ RTL/bidi تو متنِ فید — پیدا شد، نه فرضی
تو `app/today/live-feed.tsx` الان:
```tsx
<b>{f.winnerName}</b> بردِ <b>{f.loserName}</b> رو{f.score ? ` ${f.score}` : ''}
```
اسم‌ها بدونِ هیچ ایزوله‌سازیِ جهتی مستقیم تو جمله‌ی فارسی چسبیده‌ن. وقتی اسم/تگ لاتینه (خیلی از گیمرتگ‌ها همینن)، الگوریتمِ bidiِ مرورگر می‌تونه ترتیبِ «رو»/فاصله/علامتِ کنارش رو جابه‌جا نشون بده — این دقیقاً همون چیزیه که ازش پرسیدی. راه‌حلِ درست `dir="ltr"` نیست (اونم فقط برایِ اسمِ لاتین کار می‌کنه، برایِ اسمِ فارسی که تگش لاتینه ولی خودش فارسیه غلطه) — تگِ HTMLِ `<bdi>` دقیقاً برایِ همین ساخته شده («یه متنِ جهتِ نامعلوم رو بدونِ به‌هم‌ریختنِ متنِ اطرافش نشون بده»):
```tsx
<b><bdi>{f.winnerName}</bdi></b> بردِ <b><bdi>{f.loserName}</bdi></b> رو{...}
```
این فیکس مستقلِ بقیه‌ی این سنده و کمِ ریسک‌ترین تیکه‌ی کل کاره — می‌شه جداگونه و زودتر از همه انجامش داد.

### ۹.۶ سناریوی دقیق: ادمین امروز ۸ تا استوری تو ساعت‌هایِ مختلف می‌ذاره

این دقیقاً چیزیه که پرسیدی — قدم‌به‌قدم، بدونِ ابهام:

1. **ترتیبِ نوار:** ۸ حلقه، **جدیدترین‌آپلودشده اولِ نوار** (سازگار با §۴.۲ و قاعده‌ی خودِ اپ «همه‌جا جدیدترین اول»). یعنی استوریِ ساعتِ ۲۰ سمتِ راست‌ترینِ نوار می‌شینه (چون کانتینر `direction:'ltr'`ه ولی صفحه RTLه — دقیقاً مثلِ `today-news-rail.tsx`)، استوریِ ساعتِ ۸ صبح ته‌ِ نوار.
2. **رنگِ حلقه:** هرکدوم که کاربر ندیده، رینگِ رنگی؛ دیده، رینگِ خاکستری — مستقل از ترتیب.
3. **کاربر رویِ حلقه‌ی چهارم (مثلاً استوریِ ساعتِ ۱۴) تپ می‌کنه** → ویوئر تمام‌صفحه باز می‌شه، **دقیقاً از همون استوریِ ساعتِ ۱۴ شروع می‌شه** (نه از اولی، نه از آخری) — پراگرس‌بارِ بالا ۸ سگمنت داره، سگمنت‌هایِ قبل از این (جدیدتر از این، چون نوار جدیدترین-اوله) پر نشون داده می‌شن، این یکی داره پر می‌شه، بقیه خالی.
4. **عکس کاملِ سایزِ صفحه‌ی موبایل** لود و اتوپلی می‌شه (تایمر از لحظه‌ی لودشدنِ واقعیِ عکس شروع می‌شه، نه از لحظه‌ی بازشدنِ ویوئر).
5. **تپِ سمتِ راستِ صفحه** (٪۷۰ عرض) → می‌ره سراغِ استوریِ بعدی تو همون ترتیبِ نوار (یعنی به سمتِ استوری‌هایِ قدیمی‌تر، چون نوار جدید-به-قدیمه). **تپِ سمتِ چپ** (٪۳۰ عرض) → برمی‌گرده به قبلی (جدیدتر)، یا اگه رویِ اولین استوریِ این جلسه‌ست، همون استوری رو ریستارت می‌کنه.
6. **نگه‌داشتنِ انگشت** (فشارِ پیوسته، بدونِ حرکت) → همون‌جا پاز می‌شه، پراگرس هم فریز می‌شه؛ ول کردن → دقیقاً از همون‌جا ادامه.
7. **سواپِ رو به پایین** یا **تپِ ✕ (گوشه‌ی بالا)** → ویوئر بسته می‌شه، برمی‌گرده به همون جایِ نوار تو `/today` که بود.
8. **از استوریِ ۴ به سمتِ ۵، ۶، ۷، ۸ (قدیمی‌ترین‌ها) رفتن** → وقتی به آخرین استوریِ موجود (قدیمی‌ترین) می‌رسه و اون هم تموم می‌شه، ویوئر خودش می‌بنده و برمی‌گرده به فیدِ `/today` — نه لوپ، نه فریمِ خالی.
9. **هر استوری‌ای که کاملاً دیده بشه (یا تپ برایِ ردکردن بخوره)** رینگش تو نوار از رنگی به خاکستری تغییر می‌کنه (دفعه‌ی بعد که صفحه رو باز کنه).
10. اگه ادمین یه استوریِ نهم رو **همین الان**، وقتی کاربر داره استوریِ چهارم رو می‌بینه، پابلیش کنه — چیزی وسطِ دیدنِ کاربر عوض نمی‌شه (§۴.۱: ویوئر لحظه‌ی باز شدن از لیست snapshot می‌گیره)؛ استوریِ نهم فقط دفعه‌ی بعد که کاربر ویوئر رو ببنده و نوار رو دوباره ببینه ظاهر می‌شه.

## ۱۰. تصمیم‌هایِ نهایی (جوابِ کاربر، دیگه باز نیست)

۱. **تختهٔ ادمینِ حاضر/آماده:** ساده می‌شه. هیچ سیگنالِ «حاضرم/آماده‌ام» از بازیکن گرفته نمی‌شه — تختهٔ `/admin/today` فقط اطلاعاتِ موجود (اسم، حریف، دور، ایستگاه اگه دستی ست شده) رو نشون می‌ده، بدونِ ستونِ چک‌این. `MatchDesk.p1Here/p1Ready` و اکشن‌هایِ `here`/`ready` سمتِ کاربر از `/api/today/action` و `HeroCard` کلاً حذف می‌شن (فقط `ref` اگه لازم بمونه رو باید جدا تصمیم گرفت — پیش‌فرض: اونم بره، چون بدونِ حاضر/آماده بی‌معنیه).

۲. **نوارِ اخبارِ فعلی (`today-news-rail.tsx`) حذف می‌شه.** جایگزینش دقیقاً همون چیزیه که از اول گفته بودی: یه باکسِ استوری بالا، یه باکسِ اعلان زیرش. چیدمانِ نهاییِ `/today`:
   ```
   ۱. نوارِ استوری
   ۲. کارتِ «مسابقه‌ی بعدیم» + «مسیرِ من»   (فقط وقتی طبقِ جدولِ §۹.۱ صدق کنه)
   ۳. تابلوِ اعلان (§۹.۳)
   ۴. بخشِ زنده: رویداد ← استان ← فید (§۹.۴)
   ```
   `today-news-rail.tsx` و ایمپورتش از `client.tsx` حذف می‌شه؛ `newsForPlacement('today')` تو `page.tsx` هم دیگه لازم نیست صدا زده بشه.

۳. **محلِ آپلودِ ادمین تایید شد:** استوری + نوشتنِ اعلان، هر دو زیرِ `/admin/today`.

۴. **مدتِ نمایشِ هر استوری: ۸ ثانیه.** `STORY_IMAGE_DURATION_MS = 8000` — یه ثابتِ export‌شده (مثلِ `STORY_WINDOW_MS`ی ۲۴ساعته)، جدا از اون.

۵. **همه‌ی ادمین‌ها می‌تونن استوری/اعلان بفرستن — organizer نه.** یعنی چکِ نقش اینجا با پترنِ `app/api/admin/news/route.ts` (که `admin || organizer` هست) فرق داره — اینجا فقط `role === 'admin'`. (تمامِ اکانت‌هایی که نقش‌شون admin ثبت شده، نه یه ادمینِ خاص — پس محدودیتِ اضافه‌ای رویِ *کدوم* ادمین لازم نیست.)
